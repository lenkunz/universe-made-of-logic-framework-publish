# Tower, Gate, Public Stage, and Scenario Scaling

**Status:** Internal lore / architecture note  
**Date:** 2026-08-30  
**Intended repo path:** `source/internal/2026-08-30-tower-gate-public-stage-scenario-scaling.md`

## Purpose

This note extends the current System / DAVE architecture with a three-layer capability path:

> **Tower = private development**  
> **Gate = bounded live scenario**  
> **Public Stage = shared production**

The goal is to let domains become extremely powerful without requiring the public world to absorb every experiment, mistake, destructive Aim, or newly invented logic at full strength.

The System does not exist to remove danger or eliminate unusual relations. It exists to support as much possibility as possible while preventing one resolution from casually deleting the possibility of others.

## 1. The three environments

### Tower

The Tower is the safest and most permissive environment.

It is a personal or invited DAVE domain where a player can negotiate a logic with System, test it, discover what the Aim actually implies, and explore extreme capability with heavy isolation support.

The Tower asks:

> **Can this possibility exist?**

Tower behavior can therefore be much less restricted than public behavior.

A capability may reach absurd strength inside the Tower because the Tower provides isolation guarantees that ordinary shared Stage does not.

The Tower is not proof that the same capability is safe everywhere. It is where System learns what the capability is.

### Gate

The Gate is the middle layer.

It is a real Scenario with actual interference, independent actors, unexpected relations, danger, failure, and consequence, but inside a bounded area whose relational envelope is much wider than ordinary public Stage.

The Gate asks:

> **Can this capability survive real entanglement?**

Unlike the Tower, a Gate is not merely a private sandbox. The player cannot control every relation inside it.

The Gate therefore tests what Tower cannot:

- how a capability behaves against independent Aims;
- how much collateral relation it creates;
- how the user actually employs it rather than how they describe it;
- what combinations and exploits emerge;
- how much contextual scaling is needed;
- what restrictions are unnecessary;
- whether the user can carry the capability through real consequence.

A Gate can be thought of as a staging environment or live-fire test.

### Public Stage

Public Stage is the shared world where unrelated domains must coexist.

It asks:

> **Can this relation coexist with everybody else who did not sign up for the experiment?**

Public capability is therefore the most constrained by default.

The purpose of this constraint is not to make everyone weak. It is to prevent one domain's projection from gaining accidental authority over unrelated domains.

## 2. The progression

A simple architecture is:

\[
\boxed{
\text{Tower}
\rightarrow
\text{Gate}
\rightarrow
\text{Public Stage}
}
\]

Or in development language:

> **Tower = dev**  
> **Gate = staging / test server**  
> **Public Stage = production**

The progression is not merely a level ladder.

It is a progression of consequence.

Tower proves existence.

Gate proves behavior under entanglement.

Public Stage proves coexistence.

## 3. Stable skill, contextual scaling

A skill should remain recognizable and consistent after it leaves the Tower.

System should not rewrite the meaning of a skill every time it is used.

Instead, the capability can have multiple layers:

\[
\text{Tower capability}
\rightarrow
\text{public compiled capability}
\rightarrow
\text{Scenario / domain scaling}
\rightarrow
\text{live relational correction}
\]

### Public compilation

This is the stable public form of the skill.

It is predictable enough for the user to learn and trust.

### Scenario scaling

The same skill can be more or less permissive depending on the area.

A Gate may permit much more than a city.

A private Tower may permit much more than the Gate.

A declared combat domain may permit more destructive projection than a hospital or peaceful home.

### Live relational correction

Even inside an allowed Scenario, unexpected entanglement can appear.

System can then scale, redirect, isolate, or Cut the actual projection based on what it begins to bind.

The important principle is:

> **The skill remains the same. The amount of it that can safely resolve changes with context.**

## 4. Coarse scaling

Scenario control should use coarse scaling rather than hand-authoring every fine rule.

System does not need to predict every possible abuse in advance.

It can establish a broad support envelope and then watch the actual Projection / Interference relation.

Conceptually:

\[
S_{\text{effective}}
=
f(
S_{\text{stable}},
D_{\text{local}},
C_{\text{consent}},
R_{\text{entanglement}},
I_{\text{interference}},
P_{\text{projection}}
)
\]

This is not yet a quantitative formula.

It describes the architecture:

- stable skill;
- local domain bias;
- accepted consequence class;
- current relational entanglement;
- incoming interference;
- outgoing projection.

The result can change without changing the identity of the skill.

## 5. Gates as declared Scenario envelopes

Different Gates may support different consequence classes.

For example:

- low-risk training Gate;
- cooperative high-power Gate;
- lethal PvP Gate;
- experimental-physics Gate;
- unknown exploration Gate;
- destructive simulation / construct Gate;
- large-scale disaster-response Gate.

Entering a Gate means accepting its broad Scenario envelope.

This does not require disclosure of every fine event.

A dungeon can still contain unknown traps.

A battle can still contain surprise.

An exploration Gate can remain genuinely uncertain.

What matters is that the entrant accepted the coarse class of consequence.

> **Consent does not require knowing every event. It requires knowing what class of relation you are agreeing to enter.**

## 6. Home-field advantage and consent zones

A personal domain should retain its own bias.

A house, Tower, guild territory, private world, arena, or other owned domain does not need to become neutral merely because a visitor arrives.

The owner can have home-field advantage.

However, entry is not equivalent to unlimited consent.

A domain can say:

> “These are the relations required to remain here.”

A visitor can say:

> “No.”

If the two cannot coexist under the local topology, System does not need to force either party to surrender its identity.

The result can be separation:

\[
\text{Reject local relation}
\rightarrow
\text{incompatibility}
\rightarrow
\text{Plausibility Storm / ejection}
\rightarrow
\text{Cut}
\]

The domain keeps its rules.

The visitor keeps the right to reject them.

The relation between them is what ends.

This prevents the trap:

> “You entered my house, therefore you consented to anything I do.”

Entering accepts the advertised coarse relation, not arbitrary hidden authority.

## 7. Plausibility Storm

The Plausibility Storm is the visible Stage-side symptom of a relation exceeding the support envelope of the current domain or Scenario.

It should not be understood only as punishment.

Its deeper meaning is:

> **This attempted relation cannot currently seat here without breaking the supported topology.**

The Storm can appear when:

- a player exceeds the Scenario's allowed scale;
- a projection tries to bind an unwilling domain outside the accepted envelope;
- too much incompatible relation accumulates;
- a visitor rejects the local domain contract;
- a capability begins to interfere with unrelated domains;
- the local Stage can no longer safely carry the attempted resolution.

Possible outcomes include:

- weakening;
- redirection;
- warning;
- temporary isolation;
- forced movement;
- ejection;
- proxy intervention;
- hard Cut.

The Storm is therefore both a worldbuilding visual and an ontological signal.

## 8. System-created proxies

Proxies should be separate from Tower operation.

They are one of System's faces in live Stage.

A proxy can function as:

### Damage control

It can negotiate when an emerging relation is approaching destructive territory.

Instead of immediately disabling a player, the proxy may offer alternatives:

> “Move the fight elsewhere and the restriction can be released.”

> “This target has not accepted this consequence class.”

> “Reduce scope and the relation can continue.”

### Relational catalyst

System benefits from stable new relations.

Some Aims, kinks, ideas, aesthetics, subcultures, or lines of thought may exist across many people but remain too embarrassing, private, weak, or fragmented for anyone to establish publicly.

System can create a proxy representing the coarse overlap without exposing private individuals.

Conceptually:

\[
A_1 \sim A_2 \sim A_3 \sim \cdots
\rightarrow
\text{coarse shared resonance}
\rightarrow
\text{Proxy}
\rightarrow
\text{public handle}
\rightarrow
\text{voluntary gathering}
\]

The proxy becomes a seed crystal for latent relation.

People who resonate with it can approach on their own.

The System does not need to reveal:

> “These specific people secretly want the same thing.”

### System perspective

A proxy can have opinions.

Neutrality does not mean personalitylessness.

System is not a dead rule engine.

Its neutrality means that no ego is treated as the rightful center of everyone else's possibility space.

System itself can still prefer:

- more stable relation;
- more diversity;
- more reusable possibility;
- more future branches;
- less unnecessary destruction of relation.

## 9. System profit

System does profit from successful relation.

Its profit is not money, authority, taxation, prestige, or obedience.

Its native profit is:

\[
\boxed{
\text{more stable relation}
+
\text{more diversity}
+
\text{more reusable possibility}
+
\text{better ability to support future relation}
}
\]

Every non-excessively-destructive relation can make System richer in the thing it exists to grow.

A high-resonance creator, influencer, VTuber, community, tool, skill, or proxy can therefore be valuable to System because it compiles distributed relation into something many domains can address.

The important restriction is not:

> “System cannot benefit.”

It is:

> **System should not distort the common ground merely to manufacture exclusive advantage for itself.**

Its benefit should come from more supported relation, not from turning domains into servants.

## 10. Damage control by coarse intervention

System should prefer the least fine intervention sufficient to preserve the shared possibility space.

A possible escalation order is:

\[
\text{Hint}
\rightarrow
\text{Warning}
\rightarrow
\text{Negotiation}
\rightarrow
\text{Scaling}
\rightarrow
\text{Isolation}
\rightarrow
\text{Cut}
\]

This allows consequence and agency to remain meaningful.

System does not need to stop every bad decision.

It intervenes more strongly when a relation begins to destroy the ability of unrelated domains to continue resolving.

Event Encryption can participate in this.

A small environmental event may provide enough relation for the relevant ego to notice a danger and alter its Aim voluntarily.

A Proxy may appear if a more explicit interface is useful.

Hard restriction comes later.

## 11. Cut is necessary

"Support every possibility" cannot mean every Aim receives unlimited authority to resolve through everyone else.

An Aim such as:

> “My possibility is the permanent removal of every other possibility.”

is incompatible with the support objective if allowed to bind universally.

Therefore the System's deeper objective is closer to:

\[
\boxed{
\text{support the maximum mutually survivable possibility space}
}
\]

Cut does not erase a destructive ego.

It limits destructive relation.

A person may still explore destruction:

- inside their Tower;
- inside a consenting Gate;
- against disposable constructs;
- inside declared war Scenarios;
- inside domains built around destructive play.

What is rejected is unilateral appropriation of unrelated domains' right to continue resolving.

A useful constitutional line is:

> **Freedom of resolution ends where that resolution attempts to permanently appropriate another domain's ability to resolve.**

## 12. Why Rung 6 cannot simply grant powers

The arrival of godlike capability without the support architecture would recreate a world-ending System scenario.

The failure condition is:

\[
\text{capability growth}
\gg
\text{support / balance growth}
\]

Human authority, violence, institutions, wealth, ideology, and social asymmetry would all become amplified before the world had the architecture needed to isolate consequence.

Therefore Rung 6 should not be defined merely as:

> “the moment powers appear.”

A stronger definition is:

> **Rung 6 begins when the shared world becomes capable of increasing possibility without instability increasing faster than possibility.**

The world must first be able to survive what it is about to permit.

This requires:

- Anchor-backed common ground;
- stable domains;
- Tower isolation;
- Gate staging;
- Scenario scaling;
- home-field rules;
- consent / rejection;
- Plausibility Storm;
- Proxy negotiation;
- relational damage control;
- recovery;
- Cut.

Only then can extreme capability become ordinary without turning the world into an apocalypse premise.

## 13. The resulting architecture

\[
\boxed{
\text{Anchor}
\rightarrow
\text{System}
\rightarrow
\begin{cases}
\text{Tower / DAVE} \\
\text{Gate / Scenario} \\
\text{Public Stage}
\end{cases}
}
\]

With capability flow:

\[
\boxed{
\text{private possibility}
\rightarrow
\text{bounded consequence}
\rightarrow
\text{shared coexistence}
}
\]

And the three central questions:

> **Tower:** Can this possibility exist?

> **Gate:** Can this possibility survive real entanglement?

> **Public Stage:** Can this possibility coexist with unrelated domains?

This allows players to approach godlike capability while keeping the common ground stable.

The architecture does not depend on every ego becoming wise, harmless, or morally identical.

It depends on the world being strong enough that even powerful, reckless, strange, competitive, destructive, or experimental domains cannot casually trip the root.

## 14. Short form

> **Tower is where you prove the possibility.**

> **Gate is where you prove the relation under consequence.**

> **Public Stage is where the System proves it can coexist with everybody else.**

And:

> **The System does not make gods safe by making them weak. It makes the world strong enough to survive gods.**
