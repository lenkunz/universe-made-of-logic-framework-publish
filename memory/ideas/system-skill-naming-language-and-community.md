# System Skill Naming, Language, and Community

> **Status:** Speculative idea / non-canonical  
> **Scope:** System-world playground  
> **Do not treat this file as framework ground unless explicitly promoted later.**

## Core idea

The most terrifying problem in programming eventually arrives in the System too:

> **What do we name the variable?**

An endless skill relation graph cannot depend on one perfect global human-readable name for every skill.

The System therefore separates:

- **relational identity**, which is the thing itself;
- **human names**, which are handles used by communities and languages to refer to that relation.

A compact rule:

> **Skills do not need true names. They need stable relational identity.**

The names can grow around that identity.

---

# The discoverer gets the first naming opportunity

When a new reusable skill relation becomes recognized, the person or group who established it should receive the first meaningful chance to name it.

Example:

> **[New reusable skill relation recognized.]**  
> First establishment relation: confirmed.  
> Naming opportunity available.

If the discoverer names it:

> Orbit Cut

and the name is supportable, that title becomes part of the relation's early history.

This is a real reward.

The discoverer gets to seed how other people may first encounter the thing.

---

# Naming privilege is not naming sovereignty

The discoverer does not own every future word used for the skill in every language and community.

They may provide names in languages they actually choose to title.

For example:

> Thai title: provided  
> English title: provided  
> Japanese title: not provided

The System should not assume the discoverer has named the Japanese relation too.

If a later Japanese-speaking community develops and consistently uses its own title, that community can become the source of the Japanese designation.

---

# Storm is strict about empty vanity names

The System should avoid a scientific namespace filled with names that communicate nothing except the inventor's identity, nationality, institution, or ego.

Examples of weak initial formal designations might be:

> Lenium  
> Bob Technique III  
> Kingdom-X Particle  
> Supreme Founder Method

The System does not have to ban people from saying these things.

They can remain:

- aliases,
- jokes,
- historical labels,
- local nicknames,
- personal titles.

But the System-facing designation should need enough support to actually distinguish the relation.

A possible response:

> **[Designation support insufficient.]**  
> Proposed title provides little distinguishing relation to represented structure.  
> Alias registration remains available.

The basic idea is:

> **The discoverer gets first voice. The relation still has to support the name.**

---

# Person and country names are not automatically forbidden

The System should not turn the rule into a rigid "no eponyms ever" law.

Sometimes a person's name really does become the stable community handle.

If millions of people consistently know a technique as:

> Mira Step

then "Mira Step" has accumulated genuine relational weight.

The System may recognize it as a common designation because people actually use it successfully.

The important difference is:

- vanity declaration alone is weak;
- long-lived successful reference can become strong.

Origin is provenance.

Usage creates naming relation.

---

# There is no single mandatory global string

The same skill can have different valid names in different communities.

For example:

> Relational identity: R-...  
> Thai designation: เงาจังหวะ  
> English designation: Shadowstep Rhythm  
> Competitive English alias: Shade Tempo  
> Japanese designation: ...  
> Guild nickname: ...

All may point toward the same underlying skill relation.

The System does not need to declare one of these the metaphysically correct string.

---

# Neutral System translation

The System must eventually communicate across many languages.

If a discoverer has not supplied a name in a requested language, the System may provide a neutral provisional interpretation.

Example:

> Original Thai title: เงาจังหวะ  
> **[English provisional rendering: Shadow Rhythm]**

The System should not creatively invent a dramatic localized title unless some person or community actually creates that relation.

It should prefer plain functional translation.

This creates a funny incentive:

If the discoverer wants a cool English name, they should actually title it.

Otherwise the System may give them something painfully literal.

Creator:

> "Why does the English display say Purple Heat Device?"

**[SYSTEM]**

> [No creator-supplied English designation is registered.]

Creator:

> "Change it to Violet Furnace."

**[SYSTEM]**

> [Designation submitted.]

Localization becomes a real creative contribution.

---

# Community usage can establish the name

If the discoverer never supplies an English title, English-speaking users may gradually create one.

At first:

> **No established English designation.**

Then perhaps:

> **Emerging English designation: Shadowstep**

Later:

> **Common English designation: Shadowstep Rhythm**

The System is not deciding that the word is correct.

It is recognizing:

> "When this community uses this handle, it reliably resolves to this relation."

Naming is itself resonance.

---

# Multiple names can remain at once

Different communities may use different handles without one needing to erase the others.

For example:

> Common English designation: Shadowstep Rhythm  
> Competitive alias: Shade Tempo  
> Historical translation: Shadow Rhythm

The System can render whichever name is most useful for the current audience.

It should keep the underlying relation stable even when the display label changes.

---

# Functional interpretation remains separate from title

A title can be poetic.

A functional description can remain plain.

Example:

> **Title:** The Moon Forgets My Footsteps  
> **Functional interpretation:** concealment-assisted rhythmic movement

This allows human style without requiring the core to become a poet.

The title is what people call it.

The interpretation helps users understand what relation the name points toward.

---

# Names may be personalized for interpretability

The System may sometimes choose a simpler display label for a person who does not know the technical vocabulary.

A researcher may see:

> Coordinated Thermal-State Transition Timing

A chef may see:

> Thermal Rhythm

A beginner may see:

> Heat Timing

These can all point to the same relation if the context supports it.

The System should avoid pretending that the rendered label is the identity itself.

A useful distinction is:

> **Stored relation != rendered name.**

---

# Independent invention and naming collisions

Two people may independently establish strongly overlapping relations and name them differently.

Example:

> Alice: Thermal Rhythm  
> Bob: Kitchen Pulse

The System should not immediately delete one as a duplicate.

It may report:

> **[Strong relation overlap detected.]**  
> Shared structure: substantial.  
> Distinct development history: recognized.  
> Fine equivalence: unresolved.

Later, people may discover that the two are equivalent in ordinary kitchens but diverge under extreme conditions.

What first looked like a naming collision may reveal a real branch.

---

# The System should not over-centralize language

The System's role is not:

> "I declare the official English word."

Its role is closer to:

> "I can preserve the relation, translate enough for communication, and recognize which handles communities successfully use."

Language remains alive.

People continue to create:

- slang,
- professional vocabulary,
- local names,
- poetic titles,
- jokes,
- translations,
- abbreviations,
- competitive aliases.

The System learns those relations rather than replacing them.

---

# Naming itself can become expertise

Some people may become unusually good at finding a short title that captures the coarse structure of a new relation.

Possible occupations or recognized skills include:

- technical lexicographer,
- relation namer,
- terminology curator,
- designation architect,
- localization specialist.

Inventors may ask these people for help before registering a public title.

This gives naming work its own relation instead of treating language as decorative afterthought.

---

# A useful public behavior

If civilization inevitably creates twelve different things all called "Flow," the System can simply respond:

> **[12 recognized relations match the designation "Flow." Please provide context.]**

No ontology can fully save programmers from naming things `Flow`.

---

## Working principle

> **The System identifies and preserves the underlying relation. People and communities give it names. The System may translate neutrally when needed, but a name becomes strong because people successfully use it to refer to the relation, not because the System declared one global string correct.**
