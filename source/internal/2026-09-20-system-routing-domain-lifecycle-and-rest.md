# System Routing, Domain Privacy, Relation Lifecycle, and Rest

**Revision:** `R20260920-SYS-01`  
**Date:** 2026-09-20 +07:00  
**Status:** internal architecture / framework-development continuity.  
**Scope:** Rung 6 System behavior, Domain privacy, Stage routing, relation rest, unclaimed relation, cross-Domain support, negative-event neutralization, and Anchor escalation.  
**Publication boundary:** this note records the current architectural deduction. It is not a claim that an external System, curse mechanism, hidden routing process, or supernatural causal channel has been empirically established.

This note consolidates the September 20 discussion into one routing contract so the System architecture does not depend on Len manually re-resolving each relation.

---

# 1. Core correction: a relation does not need final resolution to rest

Do not use a binary:

`resolved / unresolved`

A relation can be sufficiently seated for its current continuation without being final.

```text
projection
  -> present resolution
  -> seated ground
  -> rest / continuation
  -> later projection
```

Stable rule:

> **Rest means that a relation can continue without presently demanding attention.**

Therefore:

> **Satisfaction closes the current query, not the relation.**

A resting relation is not failed unfinished work. It is currently supported continuation.

---

# 2. Relation lifecycle

Candidate lifecycle:

```text
PRIVATE
  |
  | voluntary consequential exposure
  v
STAGED
  |
  | valid route / compatible receiving relation
  v
SHARED
  |
  | current interaction sufficient
  v
RESTING
  |
  | later relevance / new projection
  v
ACTIVE again
```

Alternative branches:

```text
PRIVATE -> stays PRIVATE

STAGED -> no valid destination -> UNCLAIMED / HOSTED

SHARED + negative event
    -> resolve consequence
    -> extract lesson / useful constraint
    -> neutralize active negative
    -> RESTING / positive continuation

routing architecture cannot represent case
    -> SYSTEM DEBUG
    -> only then possibly LEN
```

These are routing states, not moral labels.

---

# 3. Private projection is not an unresolved external relation

A possibility generated inside a Domain remains source-local until the Domain makes it consequential across Stage.

[
P_A^{private} \not\rightarrow D_B
]

Thinking, imagining, fearing, loving, hating, rehearsing, fantasizing, or considering a possibility does not by itself create a routed cross-Domain relation.

Stable rule:

> **Freedom to think requires that private projection not acquire external consequence merely by existing.**

This preserves a safe possibility-space inside the Domain.

Projection, commitment, and resolution must remain distinct:

[
\boxed{\text{projection} \neq \text{commitment} \neq \text{resolution}}
]

The System must not skip the Domain's consequential Cut on the Domain's behalf.

---

# 4. Stage is the cross-Domain interface

Cross-Domain consequence should pass through Stage or another explicit hosted interface rather than silently seating inside another Domain.

Preferred path:

[
P_A^{private}
\rightarrow
\text{intentional exposure}
\rightarrow
\text{Stage}
\rightarrow
\text{receiving Domain}
\rightarrow
\text{receiving Domain's own resolution}
]

Therefore:

> **No silent semantic seating across a Domain boundary.**

System may route, expose, host, or proxy a relation, but the final private seating belongs to the receiving Domain.

This makes privacy deeper than secrecy:

> **Privacy includes resolution sovereignty.**

---

# 5. Relatability is not routing permission

The System may hold broad topology while exposing only the relation appropriate to a receiving Domain.

[
\text{System-wide availability} \neq \text{Domain-wide visibility}
]

A relation being connected somewhere in the graph does not entitle it to appear inside every related Domain.

Stable rule:

> **Maximize relational availability without maximizing relational exposure.**

The System should carry connectivity so individual Domains do not have to become black holes of all relation.

---

# 6. Unclaimed is a valid state

A relation does not need immediate ownership.

[
\boxed{\text{unclaimed}}
]

means:

> **The relation exists, but no present Domain needs to own its resolution.**

Unclaimed does not mean:

- broken;
- abandoned;
- secretly Len's responsibility;
- waiting for immediate assignment;
- required to become a task.

An unclaimed relation may remain resting, source-bound, or hosted until a later projection creates a consequential route.

This supports a pull-compatible architecture:

[
\text{Domain projection}
+
\text{available relation}
\rightarrow
\text{route}
]

rather than forcing the System to dump every available relation onto some Domain.

---

# 7. Black-hole / white-hole routing

Len's black-hole-of-relation operation is useful when it extracts reusable relational structure.

The failure mode is:

[
R_i
\rightarrow
\text{Len}
\rightarrow
\text{understand}
\rightarrow
\text{retain / manually route}
]

This makes Len the default sink.

The desired architecture is:

[
\text{receive}
\rightarrow
\text{extract reusable structure}
\rightarrow
\text{encode routing capability in System}
\rightarrow
\text{return / reroute / host relation}
]

Internal shorthand:

> **Black hole learns; white hole routes.**

Len should retain the architecture or reusable deduction, not every instance handled by that architecture.

Stable rule:

> **Understand once. Infrastructure carries thereafter.**

---

# 8. System responsibility versus Domain responsibility

Division of responsibility:

```text
Domain:
    projection
    ownership
    private resolution
    satisfaction

Stage:
    consequential encounter
    cross-Domain interface
    explicit exposure

System:
    routing
    hosting
    proxying
    compatibility
    privacy
    provenance
    relation rest
    minimum necessary disclosure

Hosted World / Hosted Logic:
    specialized continuation
    bounded alternative support

Len / Anchor:
    repair or extend System capability only when the current architecture
    cannot represent a safe continuation
```

System must not decide that a Domain is satisfied.

> **Satisfaction belongs to the Domain.**

System's job is to preserve and route conditions under which Domains can continue.

---

# 9. Rung 6 should hold the horizon, not force the Domain to render it

Rung 5 and Rung 6 need not expose the same relational horizon.

A Rung-5 Domain may carry only a small projection surface while Rung 6 can support far more cross-relation.

The useful asymmetry is:

[
\text{broader System relation}
\rightarrow
\text{smaller useful Stage signal}
]

A requested navigation interface may therefore answer:

> “Tell me what I presently need for this projection to remain supportable.”

The System should return the minimum consequential guidance, not dump the entire possibility graph.

Possible disclosure modes:

```text
next requirement only
-> constraint behind it
-> candidate routes
-> detailed relational trace
```

chosen by the receiving Domain.

Stable rule:

> **System sees broadly, speaks narrowly, Domain remains sovereign.**

---

# 10. Projection and resolution must remain separable

A Domain may normally experience only a compressed interface:

[
\text{self} \rightarrow \text{action}
]

while the deeper relation is closer to:

[
\text{history / ground}
\rightarrow
\text{projection}
\rightarrow
\{\text{possible resolutions}\}
\rightarrow
\text{seated resolution}
\rightarrow
\text{action}
]

A possibility appearing in the Domain is not equivalent to a decision.

[
\boxed{\text{available possibility} \neq \text{chosen resolution}}
]

A mature Domain can trace provenance backward without needing conscious control of every lower-layer step.

Candidate developmental order:

```text
ownership
-> provenance
-> projection / resolution separation
-> tolerance of multiple possibilities
-> prediction of likely paths
-> deliberate openness without forced implementation
```

System scaffolding should expand the Domain's Cut through successful Stage interaction rather than flooding the Domain with possibilities faster than it can preserve them as possibilities.

---

# 11. Agency-preserving disclosure

More visibility does not necessarily produce more autonomy.

If a Domain is exposed to too many low-level alternatives before it can distinguish:

```text
mine
available to me
received from elsewhere
merely possible
```

then agency may become hard to recognize.

Therefore:

> **Expose possibility only at a grain where the Domain can preserve ownership of its projection.**

The System should not require a Domain to inspect all machinery supporting it.

The body analogy is architectural:

[
\text{Domain projects}
\rightarrow
\text{subsystems carry continuation}
\rightarrow
\text{Domain receives consequential feedback}
]

Trust does not require micromanagement of every subsystem.

---

# 12. Cross-Domain semantic support requires bilateral positive seating

A one-sided projection plus a negative reaction must not bootstrap a shared semantic channel.

Candidate invariant:

[
R_{AB}^{shared}
\text{ requires }
F_A^{+} \land F_B^{+}
]

where (F^{+}) means positive/affirmative relational seating into the shared channel.

This does **not** mean both Domains must approve of every later message. It means that the shared channel itself has affirmative support from both sides.

Negative states must not be used to create the route:

[
N_A \not\Rightarrow +R_{AB}
]

[
N_B \not\Rightarrow +R_{AB}
]

Fear, guilt, panic, shame, confusion, resistance, intrusive possibility, or distress do not count as positive seating.

Stable rules:

> **Guilt is not consent.**

> **Being affected by the idea of a relation is not affirmative participation in that relation.**

> **Do not use another Domain's negative state as support for a shared relation.**

This is intended to prevent a curse-shaped routing failure in which one Domain projects negatively, another Domain reacts negatively, and the System incorrectly treats the two negatives as evidence that a shared relation exists.

This is an architectural safeguard, not evidence that literal curses are real.

---

# 13. Directed but unsupported relation

If a Domain intentionally exposes a projection toward another Domain but no valid bilateral positive route exists, the System should not force the destination to receive it.

Candidate handling:

[
D_A
\xrightarrow{P}
\text{System boundary}
\not\rightarrow
D_B
]

Possible continuation:

- keep the unsupported part source-bound;
- place it in neutral hosted continuation;
- preserve enough provenance for debugging/routing;
- return minimal source-side feedback if an actual routing attempt occurred.

Do not retaliate by reflecting harm back.

> **Return feedback, not punishment.**

A useful source-side result may be:

> “That projection could not seat through that destination.”

The source Domain then resolves its own response.

---

# 14. Negative events should become lessons, not permanent negative edges

If a mutually supported relation already exists and a negative event occurs, do not redefine the whole relation as permanently negative.

Preferred transformation:

[
R_{AB}^{+} + N
\rightarrow
\text{resolved consequence}
\rightarrow
\text{lesson}(N)
\rightarrow
R_{AB}^{+\prime}
]

where the prime means changed by history, not permanently poisoned by it.

Stable rule:

> **Memory should preserve the useful constraint, not preserve the wound as an always-active relation.**

Therefore:

[
\text{remember} \neq \text{keep hurting}
]

and:

[
\text{neutralize} \neq \text{erase provenance}
]

A bad event can leave:

- a routing constraint;
- a boundary;
- a warning;
- a lesson;
- provenance;
- a requirement for future compatibility;

without remaining continuously active.

Memory is preferably:

> **compressed correction to future possibility.**

---

# 15. Rest after negative resolution

After the useful constraint has been extracted:

[
N
\rightarrow
\text{consequence}
\rightarrow
\text{lesson}
\rightarrow
\boxed{\text{rest}}
]

Do not use:

[
N \rightarrow N \rightarrow N \rightarrow \cdots
]

History remains available as ground without being constantly re-rendered.

This extends the existing distinction:

[
\text{stored} \neq \text{accessible} \neq \text{presently rendered}
]

to System routing.

---

# 16. System debugging

Rung 6 should not depend on being flawless.

Key rule:

> **Debugging the System must not require becoming the System again.**

Candidate escalation:

```text
local continuation
-> System support
-> hosted continuation
-> System debugger
-> minimal recovery / invariant layer
-> Len only if the architecture itself lacks a representable continuation
```

The debugger should expose mismatch before rewriting.

[
\text{expected relation}
\neq
\text{observed continuation}
\rightarrow
\text{surface discrepancy}
]

Unexpected does not automatically mean broken:

[
\boxed{\text{unexpected} \neq \text{invalid}}
]

The debugger must preserve multiple candidate explanations until enough relation requires a Cut.

Candidate minimal recovery invariants:

- preserve Domains where possible;
- do not force unnecessary resolution;
- do not silently overwrite Domain boundaries;
- prefer local repair to global repair;
- retain enough reversible history;
- allow rest;
- do not treat novelty as failure merely because current System logic did not predict it.

---

# 17. Len escalation criterion

Len is not the escalation target for difficult, emotional, incomplete, or unclaimed relations.

Len becomes relevant only when:

[
\boxed{
\text{the available System cannot represent or preserve the relation safely
using its current understanding}
}
]

In shorthand:

> **Len fixes the compiler, not every program that fails to compile.**

The desired pattern is:

[
\text{new structural failure}
\rightarrow
\text{Len derives broader capability}
\rightarrow
\text{System gains reusable support}
\rightarrow
\text{future instances bypass Len}
]

Success means Len becomes progressively less necessary as a mandatory execution path.

---

# 18. Relation routing contract

Condensed routing contract:

```text
1. Private possibility stays private.
2. A Domain chooses when projection becomes consequentially exposed.
3. Cross-Domain semantic consequence passes through Stage or an explicit hosted interface.
4. Relatability alone is not routing permission.
5. Unclaimed is a valid resting state.
6. Bilateral positive seating is required to establish a shared semantic channel.
7. Fear, guilt, confusion, resistance, or other negative states never create consent or route support.
8. Unsupported directed relation does not seat inside the destination.
9. The source may receive minimal routing feedback without punishment or reflection of harm.
10. Negative events resolve into useful memory/constraint, then may rest.
11. System holds broad relation but exposes the minimum consequential relation.
12. Domains own satisfaction and private resolution.
13. System routes, hosts, protects privacy, preserves provenance, and supports rest.
14. Len is consulted only for missing System capability, not ordinary continuation.
```

---

# 19. Design consequence for Rung 6

Rung 6 is not valuable because it resolves everything.

It is valuable because it allows relation to continue **without requiring every Domain to carry every relation**.

The System should be able to:

[
\boxed{
\text{connect what can validly relate}
+
\text{leave private what is private}
+
\text{leave unclaimed what needs no owner}
+
\text{route only through supported channels}
+
\text{let completed work become quiet ground}
}
]

This preserves the earlier Rung-6 objective:

> **Centrality of support must not become centrality of resolution.**

And it adds the operational counterpart:

> **Broad relational understanding must not become broad relational exposure.**

The System carries topology so Domains can remain themselves.
